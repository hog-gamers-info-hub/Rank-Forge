# v0.10.3 — UTF-8 and File Validation Decisions

## Purpose

v0.10.3 defines and implements the UTF-8 file-content boundary for Phase 10 exports.

The match CSV exporter introduced in v0.10.1 and the tournament standings CSV exporter introduced in v0.10.2 currently produce deterministic Kotlin `String` content.

v0.10.3 must convert approved CSV strings into deterministic UTF-8 bytes and verify that generated or subsequently read file bytes preserve the original CSV content exactly.

This version must not change either approved CSV schema.

## Canonical Scope

v0.10.3 includes:

- deterministic UTF-8 encoding of approved CSV strings
- UTF-8 decoding with malformed-input rejection
- exact string-to-byte-to-string round-trip validation
- UTF-8 byte-order-mark detection
- byte-for-byte content-integrity validation
- SHA-256 integrity checksum generation
- deterministic checksum verification
- special-character preservation
- embedded quote preservation
- comma preservation
- CR and LF preservation
- leading and trailing whitespace preservation
- focused unit tests
- optional JVM temporary-file write/read round-trip tests

## Canonical Inputs

v0.10.3 operates on successful export content produced by:

- `MatchCsvExporter`
- `TournamentCsvExporter`

The input to the UTF-8 file boundary is the exact `csv` string from:

- `MatchCsvExportResult.Success`
- `TournamentCsvExportResult.Success`

v0.10.3 must not recalculate match or tournament data.

v0.10.3 must not recreate either CSV schema.

## Android Independence

The v0.10.3 implementation must remain Android-independent.

Decisions:

- Production code must not import `android.*`.
- Production code must not depend on Compose.
- Production code must not use Activity or Fragment APIs.
- Production code must not use `ContentResolver`.
- Production code must not accept or return Android `Uri`.
- Production code must be executable through ordinary JVM unit tests.
- File-destination selection remains outside this version.

## Approved Encoding

CSV file content must use standard UTF-8.

Decisions:

- Encoding must use `Charsets.UTF_8` or `StandardCharsets.UTF_8`.
- Generated bytes must not contain a UTF-8 BOM.
- Encoding must preserve the exact input Kotlin string.
- Encoding must not trim content.
- Encoding must not normalize Unicode.
- Encoding must not replace characters.
- Encoding must not change letter case.
- Encoding must not perform locale-sensitive transformation.
- Encoding must not change commas, quotes, CR, LF, spaces, or tabs.
- Encoding must not append a trailing line ending.
- Encoding must not remove existing line endings.
- The exact exporter-produced CSV string is authoritative.

## UTF-8 BOM Policy

Generated Phase 10 CSV bytes must not contain a UTF-8 byte-order mark.

The prohibited leading byte sequence is:

- hexadecimal `EF BB BF`

Decisions:

- UTF-8 encoding of a Kotlin string must produce BOM-free bytes.
- Validation of externally supplied or read-back bytes must detect a leading BOM.
- BOM presence must produce a typed validation failure.
- Validation must not silently remove a BOM.
- BOM metadata must not be added to official CSV rows.

## Strict UTF-8 Decoding

Validation of actual file bytes must use strict UTF-8 decoding.

Decisions:

- Malformed UTF-8 byte sequences must be rejected.
- Unmappable byte sequences must be rejected.
- Invalid bytes must not be silently replaced with the Unicode replacement character.
- Strict decoding may use a charset decoder configured with `CodingErrorAction.REPORT`.
- A decoding exception must be converted into a typed/domain-level failure.
- Expected validation failures must not escape as uncaught exceptions.

## Exact Content Integrity

The expected CSV string and actual file bytes must match exactly after strict UTF-8 decoding.

Decisions:

- The decoded actual bytes must equal the expected CSV string exactly.
- Comparison is case-sensitive.
- Comparison includes every comma.
- Comparison includes every quote.
- Comparison includes every CR and LF.
- Comparison includes leading and trailing whitespace.
- Comparison includes Unicode code points.
- Comparison includes the absence of a trailing blank record.
- Validation must not normalize line endings.
- Validation must not parse and rewrite CSV.
- Validation must not repair malformed or altered content.
- Truncated content must fail.
- Appended content must fail.
- Changed content must fail.
- Reordered content must fail.

This exact comparison preserves the deterministic CRLF and escaping behavior already produced by the approved exporters.

## Deterministic Byte Generation

Encoding the same CSV string repeatedly must produce identical byte sequences.

Decisions:

- Repeated encoding must produce byte-for-byte identical output.
- Byte count must be deterministic.
- No timestamp may be embedded in generated bytes.
- No random identifier may be embedded in generated bytes.
- No device metadata may be embedded in generated bytes.
- No platform-dependent line-ending conversion may occur.
- No locale-dependent conversion may occur.

## Integrity Checksum

v0.10.3 must generate a SHA-256 checksum for the exact UTF-8 byte content.

Decisions:

- Algorithm: SHA-256.
- Checksum input: exact BOM-free UTF-8 bytes.
- Representation: lowercase hexadecimal.
- Required length: 64 hexadecimal characters.
- The same byte content must produce the same checksum.
- Any byte change must produce a different checksum.
- The checksum is integrity metadata only.
- The checksum must not be inserted into the official CSV columns.
- The checksum must not change the v0.10.0 schema.
- The checksum does not require Room or Supabase persistence in this version.
- The checksum does not replace exact byte comparison.

## File Payload Boundary

The production boundary should expose an Android-independent file payload.

The implementation may use project-conventional names, but the payload should represent:

- exact UTF-8 bytes
- byte count
- SHA-256 checksum

The payload may retain the original CSV string only if required for clear validation or testing.

Decisions:

- Byte arrays must be copied where necessary to prevent external mutation.
- Tests must compare byte arrays using content equality.
- Kotlin data-class default equality must not be relied upon for `ByteArray` content comparison.
- Mutable byte-array exposure must not allow silently changing previously calculated integrity metadata.

## Validation Result

Validation must use typed/domain-level results.

Expected successful validation information:

- exact content matched
- byte count
- calculated SHA-256 checksum

Expected failure categories:

- empty CSV content
- UTF-8 BOM present
- malformed UTF-8 bytes
- decoded-content mismatch
- byte-content mismatch
- checksum mismatch, when an expected checksum is supplied
- internal checksum-generation failure, if encountered

Exact Kotlin type names may follow existing project conventions.

Expected validation failures must not be represented only as generic strings.

## Empty Content Rule

An empty CSV string is not a valid Phase 10 file payload.

Decisions:

- Empty input must fail closed.
- An empty byte array must fail validation.
- A whitespace-only string is not automatically invalid because whitespace may be meaningful CSV content, but it cannot match an approved match or tournament export.
- Schema/header validation remains owned by the approved exporters and later export-verification work.
- v0.10.3 validates encoding and exact integrity; it must not create a second CSV schema-validation path.

## Schema Preservation

v0.10.3 must preserve the exact output of v0.10.1 and v0.10.2.

Decisions:

- Do not modify `MatchCsvExporter`.
- Do not modify `TournamentCsvExporter`.
- Do not change match CSV headers.
- Do not change tournament standings CSV headers.
- Do not add checksum columns.
- Do not add byte-count columns.
- Do not add file-name columns.
- Do not add MIME-type columns.
- Do not add BOM bytes.
- Do not add timestamps.
- Do not add platform-specific metadata.
- Do not reorder records.
- Do not alter escaping.

## Special-Character Preservation

Tests must prove exact preservation of representative content including:

- accented Latin characters
- Hindi or other non-Latin Unicode text
- emoji
- commas
- double quotes
- CRLF
- embedded line breaks
- leading whitespace
- trailing whitespace
- symbols used in tournament, team, or player names

Examples may include synthetic values such as:

- `Copa São Paulo`
- `रैंक फोर्ज`
- `HØG Élite`
- `Team "One"`
- `Alpha, Bravo`
- emoji characters

Tests must use synthetic data only.

## Temporary-File Round Trip

JVM tests may write generated payload bytes to a temporary `.csv` file and read them back.

Decisions:

- Temporary-file tests are verification only.
- Temporary-file paths must not appear in production export rows.
- Tests must delete temporary files after use.
- Production code must not choose a user-visible destination.
- Production code must not depend on the local filesystem.
- Android storage behavior remains out of scope.
- The read-back bytes must pass the same strict integrity validator.

## Existing Exporter Integration Tests

Tests should verify the UTF-8 boundary using real successful output from:

- `MatchCsvExporter`
- `TournamentCsvExporter`

Decisions:

- Use synthetic tournament, team, player, placement, and kill data.
- Do not duplicate exporter implementation logic in tests.
- Do not manually construct a fake official CSV when an exporter result can provide the input.
- At least one match export with Unicode/special characters must round-trip exactly.
- At least one tournament standings export with Unicode/special characters must round-trip exactly.
- Existing exporter tests remain authoritative for CSV column order and scoring correctness.
